# #2 DPO run

- Set out to: build preference pairs from our own data and run DPO with SFT as the reference (issue #2 body). Code in #26.
- Ran: `lab pairs` and `lab dpo` at commit `0263788`, clean, one seed (`provenance` in both run files); times contended by another project's GPU jobs. The pairs run was expected to pass the one-hour limit; the owner agreed on 2026-10-03.
- Pairs: 500 greedy answers, 105 rejected (format 1, repetition 104, of which 66 never stopped), 2 ambiguous, 0 eval prompts among them (`outputs/pairs/manifest.json`, `counts`, `split_check`).
- DPO: 95 train and 10 held-out pairs, 18 steps; held-out loss 0.693 to 0.058 (`outputs/dpo/summary.json`, `eval_before`, `eval_after`). A fit check, not the eval.
- Found: on held-out pairs rejected log-prob fell (-64.718 to -123.960) while chosen barely moved (-281.671 to -286.481) (`eval_logps/*`).
- Found: under SFT a loop costs -0.182 per token against -2.250 for a reference, which is why greedy decoding loops (`held_out_lengths.before`).
- Limits: 10 pairs from training prompts; rejected about 2.9 times longer than chosen (356.4 vs 124.1 tokens, `held_out_lengths`), so "shorter wins" is confounded. Eval in #3.
- Memory: peak 13.19 GiB against 8.10 GiB for SFT (`peak_memory_gb` in both summaries); GiB, since `accelerator_memory_gb` divides by 2^30.
